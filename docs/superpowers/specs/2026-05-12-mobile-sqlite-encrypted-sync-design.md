# 移动端 SQLite 加密存储与同步设计

## 背景

`account-app-mobile` 需要从仅供展示的本地 Mock 状态，推进到“本地可落库、可加密、可按策略同步”的实现模型。

这次设计只覆盖移动端本地数据与同步策略，不改页面路由、provider 结构或后端协议细节。

## 本次目标

本次调整后，产品与文案层面的预期如下：

1. 点击用户卡片进入个人信息页。
2. 同步策略设置移动到个人信息页，不再放在原来的概览位置。
3. 同步模式只保留两种：
   - 自动同步
   - 仅本地保存
4. 自动同步采用“先写本地 SQLite，再在有网时异步上传”的模型。
5. 关闭自动同步后，数据只写入本地 SQLite，但仍允许后续手动同步。
6. support 层文案辅助函数需要能表达：
   - 自动同步开启时的详情文案
   - 自动同步关闭时的详情文案
   - 手动同步按钮文案

## 范围

包含：

- 本地记账数据写入 SQLite
- 本地敏感数据加密存储
- 个人信息页中的同步策略说明
- 自动同步 / 仅本地保存两种模式的文案与交互语义
- 手动同步入口的文案支持

不包含：

- 页面组件、provider、路由结构调整
- 后端数据库或服务端解密策略
- 多设备冲突合并
- 后台常驻同步守护进程

## 入口与页面信息架构

### 用户入口

- 用户在资料概览区域点击用户卡片，进入个人信息页。
- 个人信息页承接原先资料展示职责，并新增同步策略设置说明。

### 同步策略入口

- 同步策略相关配置统一放在个人信息页。
- “我的”页如果仍保留同步摘要，只承担状态展示，不再作为策略配置主入口。

这样可以把“用户资料”和“数据保存 / 同步策略”放到同一语义区域，避免设置分散。

## 同步模式设计

### 模式一：自动同步

自动同步是默认推荐模式，核心行为如下：

1. 用户新增或编辑记账数据时，先立即写入本地 SQLite。
2. 本地写入成功后，将记录标记为待同步。
3. 在设备有网络时，异步上传待同步记录。
4. 上传成功后，更新本地同步状态。
5. 上传失败时，保留本地记录，并在后续继续重试或允许用户手动触发同步。

这个模型的关键点是“本地写入优先”。无论网络是否可用，用户先获得本地成功反馈，再由同步流程异步追赶。

### 模式二：仅本地保存

关闭自动同步后：

1. 所有数据仍正常写入本地 SQLite。
2. 不自动发起上传。
3. 本地记录可以保留待同步状态，供后续手动同步使用。
4. 用户在需要时可主动点击手动同步按钮上传。

这个模式适用于用户明确不希望自动上传，但仍接受之后按需同步的场景。

## 本地存储与加密

### 存储模型

- 所有业务数据先写入本地 SQLite。
- SQLite 是移动端唯一可信的数据落盘层。

### 加密边界

- 敏感业务载荷以加密形式写入 SQLite。
- 同步上传时发送加密后的业务载荷，而不是明文账目内容。

### 密钥来源

- 继续采用用户设置的同步口令派生本地加密密钥。
- 不内置固定业务密钥。

## 同步状态语义

建议继续使用现有三类同步状态表达本地记录：

- `pending`：已写入本地，等待上传
- `synced`：本地与远端已一致
- `failed`：最近一次上传失败，但本地数据仍保留

在自动同步与仅本地保存两种模式下，这三类状态的含义保持一致，差别只在于“是否自动发起上传”。

## 文案与 support 层要求

`statistics-profile-support.js` 需要承担同步摘要文案的拼装职责，并支持以下语义：

### 自动同步开启

详情文案需要体现：

- 数据已先保存到本地
- 有网络时会自动同步
- 如有必要，追加失败数 / 待同步数

示例：

- `最近更新 5月11日 12:40 | 已保存到本地，有网时自动同步，待同步 2 条`
- `最近更新 5月11日 12:40 | 已保存到本地，有网时自动同步，失败 1 条`

按钮文案：

- `立即同步`
- `重试同步`

### 自动同步关闭

详情文案需要体现：

- 当前只保存在本地 SQLite
- 用户后续仍可手动同步
- 如存在待同步记录，需要补充数量

示例：

- `最近更新 5月11日 12:40 | 仅保存在本地，可稍后手动同步，待同步 3 条`

按钮文案：

- `手动同步`

### 兼容要求

- 旧调用路径仍可继续使用原有摘要文案逻辑。
- 新模式文案通过可选参数扩展，不要求同步修改页面组件。

## 数据流

### 自动同步开启

1. 用户提交记账数据
2. 写入本地 SQLite
3. 更新本地状态为 `pending`
4. 网络可用时异步上传
5. 成功后更新为 `synced`，失败则标记为 `failed`

### 自动同步关闭

1. 用户提交记账数据
2. 写入本地 SQLite
3. 保留待同步信息
4. 不自动上传
5. 用户手动触发同步时再执行上传

## 错误处理

需要覆盖以下场景：

- SQLite 写入失败
- 加密失败
- 网络不可用导致异步上传失败
- 手动同步失败

原则：

- 不丢失本地数据
- 优先给出清晰同步状态
- 自动同步失败不影响本地继续记账

## 测试要求

本次至少覆盖以下测试点：

- support 层能根据自动同步开关生成不同详情文案
- support 层能根据自动同步开关生成正确按钮文案
- 旧同步摘要文案逻辑保持兼容
- 仅本地保存模式下仍能表达后续手动同步语义

## 结论

本次设计把移动端同步模型收敛为两种明确模式：自动同步、仅本地保存。

两种模式都以“先写本地 SQLite”为前提，区别仅在于是否自动发起远端上传。同步策略入口统一进入个人信息页，support 层负责承接对应文案表达，并保持对旧调用方式的兼容。
