# 移动端 SQLite 加密存储与手动同步设计

## 背景

当前 `account-app-mobile` 已具备本地 Mock 记账流程，但数据主要停留在内存态与轻量持久化层，现有“同步”也仍是展示态，不具备真实的数据落盘、口令保护和手动上传能力。

这次调整只作用于 `account-app-mobile`，目标是把移动端从“可演示的 Mock”推进到“本地可保存、可加密、可手动同步”的单机版本。

## 目标

本次设计完成后，移动端应满足以下结果：

- 账目、账户、分类等核心本地数据落到 `SQLite`
- 本地落盘的敏感业务数据以加密形式保存
- 用户通过“同步口令”派生密钥，而不是使用内置固定密钥
- 用户可在界面上主动点击按钮，执行手动上传同步
- 上传链路发送加密后的业务载荷，不发送明文账目内容
- 现有首页、明细、统计、我的、交易编辑等页面尽量复用现有状态选择器与界面结构

## 范围

包含：

- `account-app-mobile` 本地持久化从现有轻量存储迁移到 `SQLite`
- 新增同步口令设置、解锁、重置入口
- 新增本地数据加密与解密流程
- 新增手动上传同步按钮与同步状态流转
- 调整现有状态层，使页面从 `SQLite` 仓储获取和回写数据
- 为新行为补充测试与文档

不包含：

- `account-app-sever` 的数据库切换
- 自动后台同步
- 多设备冲突合并
- 用户登录与账号体系
- 生产级密钥托管体系
- 完整离线优先同步协议

## 方案对比

### 方案 A：在现有状态层下引入 SQLite 仓储、口令加密与手动同步

做法：

- 保留现有 `useMockApp` 作为页面消费入口
- 在状态层下接入 `SQLite` 仓储
- 将交易等敏感数据序列化后加密保存
- 在“我的”页增加口令与手动同步入口

优点：

- 改动边界清晰
- 现有 UI 复用率高
- 适合分阶段替换 Mock 基础设施

缺点：

- 会存在一段“UI 已真实、状态层仍兼容旧结构”的过渡期

### 方案 B：彻底重写为 SQLite 唯一数据源

做法：

- 页面直接围绕数据库查询模型重写
- 现有 Mock 状态层整体退场

优点：

- 结构最干净

缺点：

- 改动面过大
- 容易影响当前已可运行页面

### 方案 C：只增加导出式手动同步，不改本地主存储

做法：

- 保留现有本地存储
- 仅在同步时导出加密数据包

优点：

- 开发最快

缺点：

- 不满足“本地使用 SQLite 数据库”的核心目标

### 结论

采用方案 A。

它能在不推翻当前移动端结构的前提下，补齐本地数据库、口令加密和手动同步三条主线，也为后续接真实后端预留清晰接口。

## 架构设计

整体分为四层：

1. 页面层  
   继续由 `app/(tabs)` 与 `app/transaction/*` 消费统一的应用状态。

2. 应用状态层  
   保留 `MockAppProvider` 的消费方式，但内部从“纯 Mock reducer”演进为“仓储 + 选择器 + 同步动作”的桥接层。

3. 本地仓储层  
   新增 `SQLite` 访问模块，负责表初始化、增删改查、同步队列读取、事务写入。

4. 安全与同步层  
   包含口令派生、加解密、同步载荷封装、手动上传执行和结果回写。

页面不直接访问数据库，也不直接操作加密逻辑。页面只调用状态层暴露的动作。

## 数据模型

### 本地表

建议至少引入以下表：

- `transactions`
- `accounts`
- `categories`
- `sync_jobs`
- `app_meta`

### 字段策略

敏感业务内容采用“明文元数据 + 加密载荷”分层保存。

例如 `transactions`：

- 明文字段：
  - `id`
  - `created_at`
  - `updated_at`
  - `sync_status`
  - `deleted_at`
  - `cipher_version`
- 加密字段：
  - `encrypted_payload`
  - `payload_nonce`

`encrypted_payload` 内部保存完整交易业务对象，例如：

- `type`
- `amount`
- `categoryId`
- `accountId`
- `note`
- `transactionAt`

账户与分类也使用同样的模式，以免这些信息在本地直接暴露。

### 为什么保留少量明文字段

完全全量加密会让待同步筛选、增量更新和软删除成本明显上升。保留少量非敏感元数据可以降低列表查询与同步管理复杂度，同时不直接暴露账目内容。

## 加密设计

### 密钥来源

用户在应用内设置“同步口令”。系统不内置固定业务密钥。

### 密钥派生

使用口令派生函数从用户口令生成对称密钥，并在本地保存：

- `salt`
- `kdf_version`
- 必要的派生参数

不保存明文口令。

### 本地加密边界

以下数据以加密载荷形式保存：

- 交易主体
- 账户名称与余额相关主体
- 分类名称与类型主体

以下元数据可明文保存：

- 记录主键
- 同步状态
- 时间戳
- 加密版本
- 删除标记

### 上传加密边界

手动同步时，不上传明文业务对象。上传内容只包含：

- 记录类型
- 记录 id
- 操作类型（新增、更新、删除）
- 加密载荷
- nonce / iv
- cipher 版本
- 时间戳

服务端未来是否解密，不在本次范围内。本次只保证移动端上传的内容不是明文。

## 口令与解锁流程

### 首次使用

1. 用户进入“我的”页
2. 系统提示设置同步口令
3. 输入并确认口令
4. 系统生成盐值与派生参数
5. 初始化本地加密能力
6. 后续新增或修改数据时，写入加密记录

### 日常使用

应用启动后默认处于“已落盘但未解锁”或“已解锁”状态，具体实现由启动流程决定，但同步动作必须要求当前口令已解锁。

如果用户尚未解锁：

- 可浏览是否允许由实施阶段决定
- 但不可执行手动同步
- 需要先输入口令完成解锁

### 重置口令

口令重置本质上是重新生成密钥并对本地数据重新加密。

如果实现成本过高，可将第一期限制为：

- 仅支持在已解锁状态下重置口令
- 重置过程中对现有本地记录执行重新加密

不采用“忘记口令后无损恢复”的承诺。

## 手动同步设计

### 入口

在“我的”页现有同步区域增加主按钮：

- `手动上传同步`

当存在失败记录时，按钮文案可切换为：

- `重新上传`

### 触发条件

执行同步前必须满足：

- 已设置同步口令
- 当前口令已解锁
- 本地存在 `pending` 或 `failed` 记录

如果不满足，界面应给出明确反馈。

### 同步行为

1. 读取待同步记录
2. 组装上传批次
3. 发送加密载荷
4. 根据结果逐条或逐批更新本地 `sync_status`
5. 记录最近一次同步时间与结果摘要

### 状态流转

建议保留并扩展现有状态：

- `pending`
- `synced`
- `failed`

新增临时执行态可只存在于内存 UI，不必落库，例如：

- `uploading`

### 失败处理

上传失败时：

- 不丢失本地数据
- 记录维持 `failed` 或保留 `pending`，以实现可重试
- “我的”页展示最近失败摘要

## 页面与交互调整

### 我的页

“我的”页是这次改动的主要入口，新增以下区域：

- 同步口令状态
  - 未设置
  - 已设置未解锁
  - 已解锁
- 操作按钮
  - 设置口令
  - 解锁
  - 重置口令
  - 手动上传同步
- 同步摘要
  - 待同步数量
  - 失败数量
  - 最近同步时间
  - 最近同步结果

### 交易新增与编辑

用户新增或修改交易后：

- 数据写入 `SQLite`
- 记录自动标记为 `pending`
- 首页、明细、统计页通过状态层重新取数

### 首页 / 明细 / 统计

这些页面原则上不新增复杂操作，只切换到底层真实数据源。  
目标是让已有 UI 尽量无需重写。

## 状态层调整策略

现有 `MockAppProvider` 不直接删除，而是演进为兼容层。

建议拆出以下职责：

- `repository`：负责 `SQLite` 读写
- `crypto`：负责密钥派生与载荷加解密
- `sync`：负责上传批次与结果回写
- `selectors`：继续给 UI 提供当前月汇总、统计、同步摘要等视图数据

这样能避免页面层直接承担数据库与安全细节。

## 迁移策略

由于当前已有轻量持久化数据，迁移采用保守策略：

1. 新版本启动时先初始化 `SQLite`
2. 如检测到旧持久化数据，可尝试导入
3. 导入后的记录按新结构落库
4. 导入成功后再清理旧持久化入口

如果旧数据结构不稳定，允许第一期只迁移“自定义账户/分类”，而不承诺完整历史自动迁移，但这一点需要在实施计划中明确。

## 错误处理

需要覆盖以下错误场景：

- 数据库初始化失败
- 口令未设置
- 口令错误导致解锁失败
- 加密失败或解密失败
- 同步上传失败
- 同步成功但本地回写失败

原则：

- 错误优先暴露为明确的用户可见提示
- 不静默丢数据
- 不因一次同步失败破坏本地账本

## 测试策略

本次改动必须以测试先行推进，重点覆盖：

- 口令派生结果稳定
- 加密后可正确解密
- 错误口令无法解密已有数据
- `SQLite` 仓储的新增、更新、删除与查询
- `pending` / `failed` / `synced` 状态流转
- 手动同步只上传待同步记录
- 未解锁时禁止同步
- 同步完成后首页、统计、我的页摘要保持一致

同时保留现有选择器与状态测试，避免真实存储接入后破坏页面数据汇总逻辑。

## 验收标准

满足以下条件即可认为本期完成：

- 移动端核心数据保存到 `SQLite`
- 敏感业务内容不以明文形式落本地库
- 用户可以设置并使用同步口令
- “我的”页可触发手动上传同步
- 上传内容为加密载荷，不是明文账目
- 同步成功和失败都会正确更新本地状态
- 现有主要页面在切到新数据源后仍能正常展示

## 非目标

本期明确不解决以下问题：

- 后端如何解密与入库
- 多设备间数据去重与冲突合并
- 生物识别解锁
- 端到端密钥轮换策略
- 后台自动重试
- 生产级审计与密钥恢复方案

## 结论

本次设计将 `account-app-mobile` 从本地 Mock 版本推进为“SQLite 落盘 + 用户口令加密 + 手动上传同步”的单机增强版。

实现上不推翻现有 UI，而是在当前状态层下面补齐仓储、安全和同步能力。这能以较小风险完成这次需求，也为后续接真实服务端留下清晰演进路径。
